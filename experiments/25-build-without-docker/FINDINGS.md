# Experiment 25 — Building images without Docker

**Question.** ferry can run an image you built (`ferry image load`) and cannot
build one. The gap is filled today by Docker Desktop or Podman, which is a
strange dependency for a stack whose first claim is that it does not need
Docker — and it is not only the user's images: `kernel/build-kernel.sh:34`
requires Docker to build the guest kernel, and `ferry node-image` drives
`docker buildx` with the `docker-container` driver
([18-node-image/build.sh:62](../18-node-image/build.sh)). Three callers, one
missing Linux build box.

So: can ferry host the builder itself, and what does it cost against the
alternatives?

Run on macOS 26.6.2, Apple M4 Max, 16 cores, 128 GiB. Kubernetes v1.37.0,
buildkit v0.29.0, buildctl v0.29.0 from Homebrew.

## The answer

**Yes, and the substrate is not what decides it.** Once the builder pod is
sized like the VM it is being compared against, ferry builds in the same time
as Docker Desktop and colima — within noise on every workload — and costs
**330 MiB to keep available instead of 1,741 or 1,024**.

The two things that *do* decide it are pod sizing and the handoff, and both are
ferry's to get right.

## What was actually measured

The temptation was to drive each stack the way its own users would — a pod for
ferry, `docker buildx` for Docker, `nerdctl` for colima — and that would have
measured three buildkit configurations as much as three substrates. buildx's
default driver does not even accept an output type that skips the export, so
the cell separating build time from export time could not have been run on it.

So every stack runs the **same daemon and the same client**: moby/buildkit
v0.29.0 with identical flags, driven by the buildctl already on the Mac. The
only difference is what the daemon sits inside, and therefore the address:

| stack | buildkitd runs in | reached at |
|---|---|---|
| ferry | a pod — a virtual machine of its own | the pod's real IP, `10.161.0.x:1234` |
| Docker Desktop | a container in Docker's VM | `127.0.0.1:1234`, a published port |
| colima | a container in colima's lima VM | `127.0.0.1:1235`, a published port |

The handoff is held still too: every stack exports `type=oci` and hands the
tarball to `ferry image load`, so the image reaches the same store by the same
path and the export is charged to all three alike.

Phases are timed separately rather than blended, because a blended number hides
which part belongs to the substrate. `npm` and `pip` do not care whose kernel
they are on; the export and the load are entirely the substrate's business.

**ferry needs no port-forward.** buildctl on the Mac dials the pod at the
address Kubernetes knows it by, because the Mac is already on the pod's vmnet
subnet ([docs/POD-NETWORK.md](../../docs/POD-NETWORK.md)). Docker and colima
both need a published port to be reachable at all. That is a real ergonomic
difference and it cost nothing to get.

## What the numbers say

### The substrate is a wash, and that is the result

On the incremental loop — the thing a person does fifty times a day — every
stack lands between 0.64 s and 0.96 s on the node workload and within 0.4 s of
each other on the fat one. Cold builds agree to within a second once sizing is
equal. There is no throughput argument for or against running the builder in a
pod VM, which means the decision can be made on the standing cost, where the
difference is 3–5×.

### Pod sizing was the entire gap, and it looked like an architecture result

The first ferry run built the node workload in **16.78 s** against Docker's
7.98 s, and the obvious reading was that a pod VM is twice as slow. It is not.
ferry's default pod is 2 CPUs and 512 MiB; Docker Desktop's VM on this Mac is
16 CPUs and 15.6 GiB, and `docker buildx` gets all of it. Sized at 8 CPUs and
4 GiB the same build takes **7.59 s** — marginally faster than Docker, from the
same daemon, on the same machine, within the same minute.

`npm install` on 2 cores is slower than `npm install` on 16 for reasons that
have nothing to do with whose kernel it is. **A `ferry image build` that
inherits the default pod size ships that 2× as a property of ferry.** The
builder has to be sized deliberately.

The load column moved with sizing too, and by more than expected: 0.97 s to
0.17 s on node, 4.61 s to 0.51 s on fat. That is `ferry image load` unpacking
an image to ext4, and on the fat workload the small builder was nine times
slower at it.

### The handoff is most of the incremental loop, and it is pure overhead

Split the incremental row for the fat workload on the sized builder:

| | |
|:--|--:|
| build | 0.23 s |
| export to an OCI tarball | 0.84 s |
| load into ferry's image store | 0.43 s |
| | |
| **total** | **1.50 s** |

**The build is 15% of it.** The other 85% is serialising an image out of the
builder and unpacking it back in — a full copy of 449 MB through the Mac, to
move a result from one place on the Mac to another. On the node workload it is
0.61 s of 0.86 s, so the shape holds at a quarter the size.

That is the strongest argument in these numbers for importing directly from the
builder's content store into ferry-cri instead of round-tripping a tarball, and
it gets stronger as images get bigger. It is also the only place where a
substantial win is still available — everything else is already at parity.

### The standing cost is where ferry actually wins

330 MiB for a buildkitd pod against 1,741 MiB for Docker Desktop's VM and
1,024 MiB for colima's — and those two are *floors*, paid before buildkitd
exists, because the VM has to be there for a container to run in. ferry's 330
MiB is the builder itself and there is nothing underneath it.

Two notes on the instruments, per [docs/BENCHMARKING.md](../../docs/BENCHMARKING.md):

- ferry's figure is a delta across starting the builder pod, read host-side
  with `vmmap` — valid here because a ferry pod VM is small enough to resolve.
- Docker's and colima's are the whole VM, read host-side, with the in-guest
  `used` beside it. `vmmap` was expected to saturate on Docker's VM — the
  benchmarking doc records it pinned at exactly 14,848.0 MiB — and it did not
  here, reading 1,741 MiB against the README's independently measured
  1,685 MiB for "Docker before any cluster". Saturation depends on how much of
  the allocation has been touched, and a Docker that has just started and run
  one container has not touched much.

The per-build idle-mem deltas in `results/raw.tsv` say Docker's builder costs
39 MiB and colima's costs 2 MiB. Both are true and both are useless: they price
a container inside a VM that was already running. `cost.sh` exists because of
that trap.

## Cold start, and why it was not what it looked like

The battery could not quote a `start` time for ferry: the manifests forced
`imagePullPolicy: Always` to work around the digest bug below, so every start
included a re-pull and the readings ran 1.2 s to 104 s. With that bug fixed the
pull could be dropped, and the question became worth asking properly — because
"keep the builder warm" is a much weaker recommendation if starting one is
cheap.

Five runs with the image already present:

```
1700 ms   1663 ms   1672 ms   1659 ms   82167 ms
```

Four readings inside 41 ms of each other, and one 49× worse. Splitting the wait
at the pod reporting `Running` found the whole of it on one side:

| run | to Running | to answering | difference |
|--:|--:|--:|--:|
| 1 | 668 ms | 3748 ms | 3080 ms |
| 2 | 646 ms | 41974 ms | 41328 ms |
| 3 | 630 ms | 3712 ms | 3082 ms |
| 4 | 614 ms | 723 ms | **109 ms** |
| 5 | 630 ms | 162683 ms | 162053 ms |
| 6 | 637 ms | 3712 ms | 3075 ms |

**ferry's half is 614–668 ms and never varies** — scheduling, the ext4, the VM
boot, all of it. Everything unstable is after the pod is running, and it is not
buildkitd either: its own log goes from first line to `running server on
[::]:1234` in **44 ms**.

`reachability.sh` split the remainder into the address being published, a TCP
socket opening, and buildctl completing a request. It is entirely the socket —
buildctl adds ~45 ms on top of whenever TCP starts working — and the slow runs
are exactly the ones handed a pod address a previous pod had used:

| run | address | to TCP |
|--:|:--|--:|
| 1 | 10.161.0.3 | 42,853 ms |
| 2 | 10.161.0.5 | 2,236 ms |
| 3 | 10.161.0.3 | 164,858 ms |
| 4 | 10.161.0.5 | 2,229 ms |
| 5 | 10.161.0.5 | 62,159 ms |
| 6 | 10.161.0.3 | 2,236 ms |

### It is the Mac's ARP cache

`arpstall.sh` catches it in the act:

```
pod            10.161.0.7
ARP says       6a:be:32:ea:33:5d
pod really is  86:0a:c6:11:d2:91
socket opened after 2184 ms
ARP now says   86:a:c6:11:d2:91
```

The Mac is on the pod subnet natively — the design decision
[docs/POD-NETWORK.md](../../docs/POD-NETWORK.md) argues for at length, and the
reason buildctl can dial a pod with nothing forwarded. The cost of it is that
the Mac keeps an ARP entry per pod address, and macOS holds those for minutes.
Hand a freed address to the next pod and the host is pointing at a MAC that no
longer exists; nothing from the Mac reaches that pod until the entry is
revalidated. The pod is `Running` and healthy on its own network the whole
time, so it presents as a pod that works from inside the cluster and not from
the Mac.

Nothing announces the new MAC. vmnet's DHCP is disabled
(`PodNetwork.swift:51`) and the address is configured in the guest by Apple's
vminit, so there is no gratuitous ARP for ferry to send.

What ferry controls is *which* address it hands out, and it was choosing the
worst one available: `reusable.popLast()` — the most recently freed address,
the one the host is likeliest to still remember. Preferring an address nothing
has used yet, and recycling oldest-first only once a /24 is exhausted:

| | before | after |
|:--|--:|--:|
| TCP reachable after Running | 2,236 – 164,858 ms | **79 – 88 ms** |
| cold builder start, mean | 17,772 ms | **867 ms** |
| cold builder start, typical | 1,663 ms (best of 5) | **704 – 746 ms** |

Six consecutive runs, no outliers. `ferry-cri` is 15 lines different.

**This is not a build-specific bug.** Any pod that lands on a recycled address
is unreachable from the Mac for seconds to minutes — `kubectl port-forward`,
anything the host talks to directly, any dev loop that restarts a pod. Builds
merely hit it constantly, because restarting one builder in a loop is the
fastest way to recycle an address.

## `ferry image build`, against the workflow it replaces

The battery above held the handoff still on purpose — every stack exported an
OCI tarball and every stack loaded it with `ferry image load` — so that it
measured substrates rather than workflows. That is the wrong comparison for
the shipped command, because nobody using Docker for Kubernetes development
loads their image with `ferry image load`. They run `kind load docker-image`,
which is a copy into another VM over another path.

`loop.sh` times the two real loops instead, from an edited source file to a
cluster that can run the result, both builders warm and both caches hot:

| workload | `ferry image build` | `docker buildx build` + `kind load` | |
|:--|--:|--:|--:|
| tiny | **0.47 s** | 1.02 s | 2.2× |
| node, 92 MB | **1.34 s** | 2.08 s | 1.6× |
| fat, 449 MB | **5.37 s** | 6.69 s | 1.2× |

Three runs each, best of three, and the spread within each cell is under
0.4 s. The Docker column splits roughly 0.5 s of build and the rest of `kind
load` — its build is as fast as ferry's, and getting the result into a cluster
is where it loses. ferry does the same work (export, then unpack to ext4) and
does it faster, and the advantage narrows as the image grows because ferry's
unpack is the part that scales with size.

**The lead shrinks with image size, and that is the honest shape of it.** At
449 MB ferry is 1.2× rather than 2.2×, and the remaining cost on ferry's side
is almost entirely the ext4 unpack — a pod is a VM and needs a block device,
so there is no overlay to hand it a stack of layers. Making large-image
rebuilds fast means unpacking incrementally: the previous rootfs cloned and
only the changed layers applied, which the digests make knowable. That is the
next real optimisation and it is not done here.

## Five bugs found on the way, and why the worst one looked recurrent

The last two were found by building the feature rather than by benchmarking it,
and either one on its own would have made `ferry image build` unusable.

### A rebuilt tag ran the old image

The worst of them, and invisible from outside: the rootfs was keyed on the
image's *name*, and unpacked to `image-<name>.ext4`. A tag is not a stable
identifier — `myapp:dev` built twice is two different images — so the second
load found `rootfsCache["docker.io/library/myapp:dev"]` already set and reused
the first image's root filesystem, while the file name collided too.

Demonstrated with a marker file: built and loaded `VERSION-TWO`, ran the pod,
got `VERSION-ONE`. The build reported success, the load reported success, and
`ferry image ls` showed the new image. Only the running container disagreed.

**This is the loop the feature exists to serve** — edit, rebuild the same tag,
run it — so it would have hit on the second iteration of the first thing anyone
tried. Fixed by keying the rootfs on the image digest and making names aliases
for it; verified with the same marker test, which now prints `VERSION-TWO`.

### Every build leaked a root filesystem

Keying on the digest means a new ext4 per build, and nothing collected the old
one: 4 GiB per rebuild of the python image, on a disk that was already at 96%.
It also made the fat workload's timings meaningless — 27 s, 23 s, 5 s across
three runs — because writing 4 GiB onto a nearly-full APFS volume is as
variable as that. With the leak fixed the same cell runs 5.4, 5.6, 5.7 s.

The first attempt at collecting it did nothing, for a reason worth recording:
it asked whether anything still referenced the old rootfs, and something always
did — the superseded image's own digest key. What makes the old image garbage
is that no *tag* names it any more. An image reachable only by a digest nobody
has written down is not reachable. Collecting on that test holds the file count
flat across repeated builds (2 → 3 → 3 → 3).

### The kubelet took the image store apart on a timer

The digest bug was fixed, verified, and came back an hour later. That is worth
recording, because "we fixed it and it returned" is the shape of a wrong
diagnosis, and the second cause was a different one standing behind the first.

The kubelet's image garbage collector removes images **by image ID** — the
digest — and it runs whenever the image filesystem is over 85% full. This disk
was at 97%, partly from the rootfs leak above. `removeImage` then dropped the
key it was handed and the normalised form of it, and nothing else:

- every *name* still pointed at the rootfs, so `imageStatus` went on answering
  "present" — hence `kubectl describe` printing **"already present on machine"**
  two lines above **"has not been pulled"**;
- `createContainer`, which the kubelet calls with the ID, could no longer
  resolve it;
- and the ext4 — the only thing in this runtime that occupies disk — was left
  behind, so nothing was freed. The collector saw the same 97%, ran again five
  minutes later, and took the next image apart.

```
image_gc_manager.go:529 "Removing image to free bytes" imageID="sha256:0039c1d4…"
kubelet.go:1750 "Image garbage collection failed multiple times in a row"
  … Failed to free sufficient space by deleting unused images (freed 16106127360 bytes)
```

It reports freeing 16 GB and frees nothing. **That loop is what made the bug
look like it kept coming back** — it was not recurring, it was being recreated
every five minutes by a background process, and it would have done so on any
sufficiently full disk regardless of what else was running.

Removal is now by identity: whatever the caller names, the whole record goes —
every alias, every map — and the file is deleted, so the collector actually
gets the space it asked for.

### `ferry image load` is fine; starting a pod from an image twice is not

A pod made from an image ferry-cri has already pulled fails with
`Error: not found: image sha256:... has not been pulled`, while the image is
plainly in the store — `state.json` has it, its manifest blob is on disk, and
its unpacked ext4 is sitting there. It happened on the second buildkitd pod and
is reproducible.

The kubelet passes the image **by ID** once it knows one, and
`PodRuntime.swift:1099` looks it up in `rootfsCache` by reference and by
normalised reference. The digest key is registered at
`PodRuntime.swift:1597` — but only on the branch taken when the rootfs is
unpacked for the first time. The `else` branch at `:1599`, taken when the
rootfs is already cached, copies the *name* keys across and not the digest. So
the digest key exists exactly until something takes the second path.

**Fixed.** The digest is now registered on every path rather than only the one
that unpacks, and the exact failing case — delete the pod, recreate it with
`IfNotPresent` — now runs. The manifests here no longer force a pull, which is
what made the cold-start investigation above possible at all.

### The benchmark nearly measured colima twice

`colima start` **switches the current Docker context to colima**. A bare
`docker build` after starting colima silently builds on colima while claiming
to be Docker Desktop, and produces entirely plausible numbers. Both contexts
are now named explicitly in `lib.sh`.

## Caveats

- **Cold builds carry network.** The cache is pruned before them, so the base
  image is fetched from a registry. One tiny cold build read 10.17 s against a
  1.7–1.9 s norm on the same configuration; the run was repeated and the
  outlier is in `results/raw.tsv` under `ferry-sized-tiny`. Cold-build
  differences under a second or so are not evidence of anything.
- **One run per cell**, apart from that repeat. Enough to separate 330 from
  1,741 and 16.78 from 7.59; not enough for the sub-second rows, which is why
  nothing above is claimed from them.
- **Docker Desktop was running during ferry's build cells.** The README stops
  it for ferry's runs, and that rule was written for memory measurements, which
  here are taken as deltas or as separate whole-VM readings. It does mean
  ferry's build times were set with an idle Docker on the machine — if
  anything, against ferry.
- **Apple's `container` CLI was not measured.** It is a second manager over
  `apple/containerization`, which `ferry-cri/Package.swift:10` already pins at
  0.45.0 and already drives — so the ferry rows here *are* Apple's
  containerization framework, with ferry-cri rather than Apple's daemon on top
  of it. A separate `container` install would add a daemon and an image store
  without changing the substrate.
- **Mode 2 (a container on a machine node) was not measured.** It would cost
  less than 330 MiB to keep warm, sharing the node VM's kernel — worth doing if
  the standing cost ever matters more than it does now, but `ferry machines`
  ships off by default and the pod path works on a stock install.

## What this argues for

1. **Run the builder as a pod, sized deliberately** — 8 CPUs and 4 GiB by
   default on a machine like this one, not the 2/512 a pod inherits. Sizing is
   the difference between matching Docker and being twice as slow as it.
2. **Warm is nice, not necessary.** A cold builder is ready in **0.70 s** now
   that addresses are not recycled into a stale ARP entry — against a ~0.3 s
   no-op rebuild, so starting one costs about what one trivial build costs.
   Keep it warm for the common case because 330 MiB is cheap, but an idle
   timeout that reclaims it is no longer a painful trade, and a
   builder-per-build design is defensible where it would not have been at
   17 s.
3. **All five bugs are fixed, and `tests/image-identity-test.sh` holds them
   fixed.** Source rules catch the shape of each mistake where somebody would
   make it, and an end-to-end case builds one tag twice and checks which image
   actually runs. Three of the five were the same instinct — treating a name as
   an identity — applied in three places, so the rules are worth more than the
   fixes.
4. **Then go after the handoff.** Export plus load is 85% of an incremental
   build on a large image. Importing straight from the builder's content store
   is the one substantial win left on the table — it is now clearly the
   largest, since cold start went from the worst number here to a rounding
   error.

## Reproducing

```sh
./loop.sh <tiny|node|fat>                          # ferry vs docker+kind, the shipped loop
./bench.sh <ferry|docker|colima> <tiny|node|fat>   # one cell
BUILDER_MANIFEST=buildkitd-sized.yaml TAG_SUFFIX=sized ./bench.sh ferry node
./cost.sh                                          # standing cost
./startbreak.sh                                    # cold builder start
./reachability.sh                                  # where the wait after Running goes
./arpstall.sh                                      # the stale ARP entry, caught
python3 summarize.py                               # the tables above
```

`results/raw.tsv` is append-only; `summarize.py` takes the last reading for
each cell and drops failures.
